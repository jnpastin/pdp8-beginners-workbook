## OS/8 File Encoding

In order to understand how binary files are encoded on disk, we must first understand how ASCII based text files are packed and written to disk.  The binary format borrows from this and the ASR paper tape format.  

---

### ASCII Files
When OS/8 writes files to disk it encodes them in a unique format.  The PDP-8 uses a 12-bit word length, and the standard interface device was a Teletype ASR-33.  The ASR-33 has a paper tape punch and reader integrated into it, but it uses 8 level paper tape which means that words need to be spread across multiple bytes.  In this usage, "byte" refers to a single line of holes on a paper tape, 8 bits.  This formed the basis for all of the storage encoding.

DEC chose to pack 3 characters into two words by splitting one of the characters into high and low nibbles.  Character 1 forms the least significant eight bits of Word 1, likewise for Character 2.  Character 3 is split into two 4-bit nibbles, with the high nibble being the four most significant bits of word 1 and the low nibble being the four most significant bits of Word 2.  

```
       +---------------+------------------+
WORD 1 |CHARACTER 3    |                  |
       |BITS 0-3       |  CHARACTER 1     |
       +---------------+------------------+
WORD 2 |CHARACTER 3    |                  |
       |BITS 4-7       |  CHARACTER 2     |
       +---------------+------------------+
       0              3 4                11
```

For example, the word `DOG` is represented by the ASCII characters 104, 117, and 107 in octal.  In the PDP-8 world, the 8th bit is always high for ASCII characters, so it is represented by 304, 317, 307.

In order to properly encode this, it needs to be converted to binary, then the third character needs to be split.

| Character | DEC ASCII Encoding | Binary Encoding |
| --- | --- | --- |
| D | 304 | 11 000 100 |
| O | 317 | 11 001 111 |
| G | 307 | 11 000 111 |

The third character is then split in half `1100` and `0111` and combined with the other two characters:

```
       +----+--------+
WORD 1 |1100|11000100|    6304
       +----+--------+
WORD 2 |0111|11001111|    3717
       +----+--------+
```

This yields two words `6304` and `3717` in octal.  These two words are what would be written to disk if a text file were to be saved.

---

### Binary Files

Binary files are written in a similar manner, with each word being split into two bytes.  However, since words split into 6 bit nibbles easily, the remaining two bits are used for control.  There are 4 major components to each BN file:

1. **Leaders/Trailers -** These are the one of the only times that the most significant bit is set, all other bits remain unset.  They have no semantic meaning and are a holdover from paper tape.
2. **Field Definitions -** For a field definition, both of the two most significant bits are set, followed by the 6 bits that determine both IF and DF.  This is the only other data type that is a single bit.
3. **Origins -** This is the only time that the second most significant bit is set, the remaining bits and the next word form the address that the loader will store data into memory at.  The second word does not have the second most significant bit set.  Orgins may be repeated and may appear throughout the program.
4. **Data -** Each word is split into two bytes, the upper two bits in both words are unset.
5. **Checksum -** When PAL assembles the program, it will calulcate a checksum.  When the loader reads the file, it will do the same.  If the two don't match, then an error is generated.  The checksum is generated by adding the byte values, including the origin directives, which is then packed like other words into two bytes where the two most significant bits are unset.

| Data Type | Binary Representation |
| --- | --- |
| Leader/Trailer | 10 000 000 <sup>[1]</sup> |
| Field | 11 III DDD <sup>[2]</sup> |
| Origin | 01 HHH HHH & 00 LLL LLL <sup>[3]</sup> |
| Data | 00 HHH HHH & 00 LLL LLL |
| Checksum | 00 HHH HHH & 00 LLL LLL |

[1] = Leaders and Trailers are only one byte
[2] = Field definitions, `I` for instruction field and `D` for data field
[3] = `H` is used to represent the most signficant data bits, and `L` is used to represent the least signficant data bits.  

#### Example

Consider the following simple program:

```

       CLA
       IAC
       DCA 0300
```

That would assemble to:

```
       0200  *0200
00200  7200  CLA
00201  7001  IAC
00202  3300  DCA 0300

```

## Exercise

OS/8 includes a tool called `FUTIL` that can be used to inspect the contents of files among several other functions.  FUTIL offers several ways of decoding this data into useful formats.  

A small program that increments the Accumulator until it overflows, then increments the Multiplier Quotient before looping was written and compiled.  [Source](./E1C7.PA) & [Listing](./E1C7.LS)

### ASCII File

The first file of note is a [dump of the PA file](./FUTIL_DUMP_E1C7_PA.TXT).  This file was dumped with FUTIL attempting to decode it into several different formats.

* **ASCII** - This interprets each word as an ASCII character, using only the eight least significant bits.  The four high bits are discarded, which results in every third character being omitted.
* **OCTAL** - This shows the packed data as described above.  Every two words contains three bytes, with each byte containing the DEC ASCII code for one character.
* **BYTE** - This unpacks the bytes from the words, and displays them individually.  For a text file like this, each byte represents the DEC ASCII code for the chracter that it represents.
* **OS** - This does all of the decoding work, and displays the complete, unpacked text of the file.

To validate the encoding, a small [Python script](FUTIL_UNPACKER.py) was written to decode the raw octal value.  The output of this can be seen in [this file](./FUTIL_DUMP_E1C7_PA_UNPACKED.TXT).

### Binary File

Since the dump formats were well understood at this point, and the input file in question is binary, not ASCII, the `byte` format makes the most sense.  FUTIL was used to dump the file, as written on disk, in this format.  The content can be seen in [this dump file](./FUTIL_DUMP_E1C7_BN.TXT).

Because the byte format does much of the decoding work, all that remained was to validate that the output could be used to generate a set of machine code instructions that matched those generated by PAL.  This can be seen in [this file](./FUTIL_DUMP_E1C7_BN_ANALYSIS.TXT)
